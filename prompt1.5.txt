================================================================================
1. FIX THE IMPORT SO REPAYMENT DETAILS ARE SAVED
================================================================================

1.1 THE MOST LIKELY ROOT CAUSE — FIX THIS FIRST
The file rows carry `id` and `userId`. If the importer uses the file's `id` as
the contact id, or inserts account_details with the file's `id` as
`contact_id`, every child row points at a contact that does not exist in your
database. The result is exactly the reported symptom: the contact appears in the
list, but its repayment details are missing.

Required:
- Treat `id` and `userId` from the file as UNKNOWN/IGNORED foreign keys. Never
  use them as the primary key of a contact, and never use them as
  `account_details.contactId`.
- Capture the id RETURNED by your create/update call for each contact and use
  THAT id when inserting its account rows.
- If you want to keep a trace of the source ids, store them in separate optional
  fields (`sourceId`, `sourceUserId`). They must never be used for relationships.

1.2 REPAYMENT DETAILS MUST BE WRITTEN AND VERIFIED
Treat account details as a required part of the contact payload when the file
provides it, not as an optional afterthought.

- For each contact row: after creating/updating the contact, insert one
  account_details row per entry in `accountDetails` (bank, accountNumber,
  accountName), using the returned contact id.
- Validate before saving: an account entry needs at least `bank` AND
  `accountNumber`. If `accountName` is missing, still save the entry with an
  empty receiver name and do NOT reject the whole row.
- Trim whitespace on bank / accountNumber / accountName. Do NOT change their
  casing, do NOT title-case them, and do NOT strip the bracketed company suffix
  from `accountName`.
- Upsert account rows by (contactId, accountNumber) — never create a second copy
  of an account number that already exists for that contact, and NEVER delete an
  existing account just because it is absent from the uploaded file. Re-uploading
  the same file must not duplicate or wipe repayment details.
- Verify before reporting success: count the account rows you intended to write
  and the account rows that actually exist for those contacts. If a contact ends
  up with fewer account rows than the file specified, that row is a FAILED row.

1.3 THE IMPORT MUST NEVER REPORT A FALSE RESULT
The current behaviour ("it says FAIL but imports contacts anyway") is caused by
partial writes plus a single generic error toast. Fix it:

- Process rows independently and accumulate a per-row outcome:
  `created` | `updated` | `failed` (with a reason).
- The UI must show an accurate summary, for example:
    "Imported 58 contacts — 57 created, 1 updated (2 loans), 0 failed."
  and when rows fail, list them: "Row 14: could not save account details — …"
- A generic "Import failed" message is only allowed when NOTHING was saved.
  If some rows saved, the message must state exactly how many saved and how many
  failed. Never show "failed" while contacts were in fact created.
- A row must be all-or-nothing: if a row's accounts cannot be saved, do not leave
  a half-imported contact behind — roll that row back (delete the contact you
  just created for it, or restore its previous values) and count it as failed.
- On success clear the preview and reset the file input so the same file can be
  re-uploaded immediately.
- Do not close the modal when there were failures; keep the error list visible so
  the user can fix the file and retry only what is needed.

1.4 DUPLICATE PHONES AND MULTIPLE LOANS (from the real fixture)
The fixture's duplicate phone is ONE customer with TWO loans. Do not collapse it.

- Add a `loans` child entity (contactId, loanId, amount, dayType, appType,
  dueDate, isPrimary) so a contact can hold more than one loan.
- The Contact keeps `loanId`, `amount`, `dayType`, `appType` as the PRIMARY loan
  so the header info strip and the template variables keep working exactly as
  specified in prompt1.txt.
- Import rule: normalise the phone, then
    * no contact with that phone           -> create the contact + loan 1
    * contact exists, same loanId            -> update that loan
    * contact exists, DIFFERENT loanId      -> add a second loan to that same
                                               contact and set it as primary if
                                               the contact has no primary yet
    * contact exists, accounts in the file  -> union the accounts in
- Report merges explicitly in the summary, e.g.
  "1 contact received a second loan (OD260927131211880111337, OD260927131237152105749)
   and 2 repayment accounts."
- If you decide NOT to introduce the loans entity, then you must surface the
  conflict to the user in the preview ("2 rows share phone 08032519041 with
  different Loan IDs — keep both / keep the first / cancel") and never silently
  discard one. Do not merge by overwriting.

1.5 DATA CLEANING ON IMPORT (matching the real file)
- Collapse runs of whitespace in `name` to single spaces
  ("olomola  toyin  Esther" -> "olomola toyin Esther"). Keep the original casing;
  do not capitalise or title-case.
- Keep `loanId` exactly as given (23 chars, "OD…"), trimmed, never reformatted.
- Keep `appType` exactly as given, including capitalisation, and register/find the
  app case-insensitively (see prompt1.txt §6A).
- `dayType` must be stored as a number and may be negative.
- Ignore any other unknown keys in a row rather than failing the row.

2. THE CONVERSATION SCREEN — LAYOUT THAT MATCHES WAABA
================================================================================

The screen is a vertical stack of exactly four regions, in this order:

  [ A ] CHAT HEADER          — fixed, always visible, never scrolls
  [ B ] CONTACT INFO STRIP   — fixed, directly under the header, never scrolls
  [ C ] MESSAGE LIST         — the ONLY region that scrolls
  [ D ] MESSAGE COMPOSER     — fixed, always visible, pinned to the bottom

The page itself must not scroll. Lock the document/app shell so that only region
C scrolls, otherwise the composer gets pushed off-screen by the keyboard.

2.1 [D] THE MESSAGE INPUT AREA (composer) — MUST NEVER BE HIDDEN
This is the part that is currently wrong. Requirements:

- The composer is always visible: pinned to the bottom of the screen when the
  keyboard is closed, and riding directly above the keyboard when it opens. It
  must never be covered by the keyboard, the on-screen keyboard suggestion bar,
  the browser URL bar, or the home indicator.
- Implement the keyboard behaviour with the visual viewport, exactly like Waaba:
    * listen to `window.visualViewport` `resize` and `scroll`;
    * on change, set the chat screen container's height to
      `visualViewport.height` px and its top offset to `visualViewport.offsetTop`
      px, so the whole screen (header + strip + composer) is resized to the
      actually visible area;
    * after the resize, in the next animation frame, scroll the message list to
      the newest message;
    * on unmount, remove the listeners and clear the inline height/top styles.
  (If your framework offers a `dvh`/`svh` unit or a keyboard-inset CSS variable,
  you may use it instead — but the composer must provably stay above the
  keyboard on iOS Safari, Android Chrome and desktop.)
- Respect the safe areas: add `padding-bottom: max(8px, env(safe-area-inset-bottom))`
  to the composer, and `padding-top: max(env(safe-area-inset-top), 12px)` to the
  header.
- Layout of the composer row: a round attach/menu button, a growing text input,
  and a send button. When the input is empty the send button may show a mic or a
  plus icon; once there is text it becomes the send button.
- The input must grow with content up to a maximum of roughly 5 lines, and after
  that the text scrolls INSIDE the input. The composer must never grow so tall
  that it hides the conversation.
- The input must be focusable and the keyboard must open when the user taps it.
- Keep Enter = newline and add an explicit Send button; on mobile the send button
  is the primary action (Enter must NOT send on touch devices).
- When the user sends: clear the input, reset its height to one line, scroll the
  message list to the newest message, and show the message optimistically with
  status `sending`, then update it to `sent` or `failed` (with a retry
  affordance on failure).
- Above the composer, show transient context strips when active:
  replying-to a message, editing a message, or a failed-message banner. Each has a
  close (x) button and must not permanently occupy space.
- Stacking: composer and header must have a higher z-index than the message list
  and its background, and the composer's background must be opaque so messages
  never show through it.
- If the message list is empty, show a centred empty state that still leaves the
  header, the info strip and the composer visible.

2.2 [A] CHAT HEADER
- Left: a back button (mobile only).
- Then a tappable identity block: contact avatar (initials fallback), the
  contact's NAME in bold, and a secondary line showing presence/last-seen or the
  phone number. Long names and phones must truncate with an ellipsis, not wrap
  and not push the header taller.
- Tapping the avatar or the name opens the full contact profile (see §3).
- Right: an options menu containing at least — View contact, Pin, Mute, Archive,
  Block, Move to trash.
- The header must stay a fixed height and must not change size when the presence
  text changes or a notification arrives.

2.3 [B] CONTACT INFO STRIP — directly under the header
A single compact horizontal strip showing the essentials at a glance, always
visible, never scrolling away with the messages.

- Content, in this order (chips/cards with a tiny label + value):
    Loan ID | Amount | Due Date | Day Type | App
  plus, if space allows: Phone. Due Date is computed from dayType as
  (today − dayType) formatted dd/MM/yyyy.
- Values must be truncated with an ellipsis (the Loan ID is 23 characters) and
  the strip must scroll horizontally on narrow screens rather than wrapping or
  overflowing. Never cause horizontal page scroll.
- A missing value renders as "—" (or "None" for App). Never render a default app
  name — if the contact has no app, the chip must read "None" / "—".
- If the contact has repayment details, show a chip such as "1 account" or
  "2 accounts" that opens the profile scrolled to the Bank Accounts section.
- Tapping any chip opens the full contact profile.
- When a value is edited (in the profile or elsewhere), the strip must update
  immediately without a page reload.
- Keep the strip on one line at all times; its height is fixed.

3. FULL CONTACT DETAILS + EDIT IN PLACE (tap the profile)
================================================================================

Tapping the avatar/name (or any info-strip chip) opens the full details view,
like Waaba's Contact Info panel: a full-screen scrollable sheet on mobile, and a
side panel on desktop.

3.1 VIEW MODE — sections in this order
  1. Profile block: avatar (large), contact name, phone, presence/last seen,
     and quick actions (Call/SMS, Message).
  2. LOAN DETAILS: every loan for this contact (see §1.4 — a contact can have
     more than one). Each loan card shows Loan ID, Amount, Due Date, Day Type,
     and App, with the primary loan marked "Primary".
  3. CONTACT INFORMATION: phone (normalised, tap to copy), optional email,
     labels as coloured chips.
  4. REPAYMENT DETAILS / BANK ACCOUNTS: one card per account showing
     Bank, Account Number, and Receiver's Name, each on its own line, exactly as
     it was imported (preserve the bracketed company suffix).
     This section is REQUIRED to be visible whenever the contact has accounts,
     and must show a clear "No repayment details yet" state when it does not.
  5. History summary: last message preview and time, unread count, and whether
     the conversation is pinned/muted/archived.

3.2 EDIT MODE — everything editable without leaving the screen
- Each section has its own "Edit" toggle. Toggling turns its fields into inputs
  and shows Save / Cancel for that section only. Save writes that section and
  refreshes the header info strip + the contact list immediately.
- Editable in place:
    * Contact: name, phone (re-normalised on save), and an APP selector. The App
      selector MUST include an explicit "None (no app)" option and MUST default to
      the contact's current value — never to the first app in the list. If the
      contact's app is not in your apps list, still show it as an option so
      saving cannot discard it.
    * Loans: loan id, amount, day type, app, and due date (derived from day
      type). Add a loan, edit a loan, mark one primary, delete a loan.
    * Repayment details: add an account (bank + account number + receiver's
      name), edit an existing account inline, and remove an account (with a
      confirmation). Changes must persist immediately.
    * Labels: toggle coloured chips to assign/unassign labels, plus a label
      manager if you already have one.
- Bottom actions: "Edit Contact" (full form, optional), "Move to Trash"
  (soft delete + confirm), and for trashed contacts "Restore".
- Save rules that must hold:
    - An empty field saves as empty; it is never replaced by a default.
    - Re-saving without changes must not create duplicate account rows or
      duplicate loans.
    - Phone is re-normalised on save, and if the new phone collides with another
      contact's, block the save with a clear message.
- After any edit, the profile view, the chat header info strip, and the contacts
    list must all reflect the new values without a manual refresh.
